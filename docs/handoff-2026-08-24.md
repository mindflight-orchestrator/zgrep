## Executive status

The active goal remains to build the fastest grep/egrep-compatible binaries in
Zig 0.16 without trading away GNU semantics. The Linux performance core is
strong and the current 75,031,861-byte warm-cache matrix is locally ahead of
GNU grep and ripgrep in every measured row in both `C` and `C.utf8`. This is
reproducible local evidence, not a universal cross-machine claim.

The initial baseline was committed and annotated as `v0.1` at
`23440ef756a173c22085f2ea7060550b52cab6a7`. The work described below is an
intentional uncommitted tranche on top of that tag. There is no configured Git
remote, and no new release has been created.

The goal is not complete. The current supported platform is x86_64 GNU/Linux;
macOS and Windows need a replacement for GNU regex internals and POSIX mmap.
Broader GNU option coverage, cross-platform CI, stronger benchmark statistics
and release execution also remain.

## Current uncommitted tranche

### GNU color and recursive special files

- `--color`/`--colour` implements `always`, `never`, terminal-aware `auto`, GNU
  aliases and byte-exact `GREP_COLORS` capabilities.
- Colored matches, paths, line numbers, byte offsets, separators, context,
  counts, file lists and NUL filename/data modes are differentially tested.
- Explicit FIFOs/devices retain GNU's default read behavior. Recursively found
  devices are skipped by default and read serially with `-D read`, including
  `-l`/`-L`, so the normal regular-file tree remains parallel and non-blocking.

### Remaining GNU output options

- `-T`/`--initial-tab` is byte-exact for regular files, redirected regular
  stdin, unknown-size pipes, line/byte fields, context, color, `-o`, `-z/-Z`,
  counts and file lists. It follows GNU's file-size-derived widths and the
  19-column unknown-size width.
- `--line-buffered` flushes every complete output record. Literal stdin no
  longer waits for the 256 KiB detection block in this mode, and a bounded
  circular context buffer streams `-A/-B/-C` output before EOF.
- Buffered and line-buffered stdout failures unwrap Zig 0.16's file-writer
  sentinel and report GNU's `write error: Broken pipe` diagnostic. The
  differential suite fixes `SIGPIPE` to ignored for both programs so it tests
  the deterministic `EPIPE` path rather than scheduler-dependent signal exit.
- `-U`/`--binary` is accepted as GNU's no-op on GNU/Linux. Every long option
  advertised by GNU grep 3.11's `--help` is now also parsed; the help text now
  exposes the existing group-separator and `--silent` aliases.

### Locale and Unicode

- Startup initializes the process locale through libc and recognizes UTF-8
  codesets.
- Locale-sensitive fixed, BRE and ERE semantics use GNU regex for Unicode case
  folding, word boundaries and POSIX character classes.
- PCRE mode uses `PCRE2_UTF`; invalid subject sequences use
  `PCRE2_MATCH_INVALID_UTF`, matching GNU's behavior for `-P -o`.
- Invalid UTF-8 output follows GNU's record-level binary rules: normal output
  suppresses invalid selected/context records and reports a binary match,
  `-I` suppresses those records without changing selection status, `-a` emits
  raw bytes, and `-o` emits only valid matching spans.
- ASCII subjects in UTF-8 locales use a verified hybrid: SIMD ASCII detection,
  literal/SIMD paths and PCRE2 JIT for compatible matching, while ambiguous
  `-o`/color spans preserve POSIX leftmost-longest behavior through DFA.
- `tests/locale-semantics.sh` currently proves 141 exact stdout/stderr/status
  comparisons across `C.utf8`, `en_US.utf8` and `nl_BE.utf8`, including valid
  Unicode, malformed UTF-8, long-s/dotless-i folding, recursive CJK word
  boundaries and the optimized ASCII hybrid.

### Performance work

- Large ASCII validation is parallelized and cached per mapped input when a
  locale-sensitive whole-buffer fast path requires it.
- Sparse regex `-o` now reuses bounded ordered parallel candidate discovery;
  exact spans are produced during ordered emission.
- Sparse literal and required-literal regex context on regular files larger
  than 64 MiB now discover selected records in parallel, then reconstruct
  ordered GNU context groups. Regex workers retain independent mutable match
  state. Metadata remains capped per chunk and any dense/failure path returns
  to the sequential scanner before emitting a byte. The same path feeds the
  existing color-aware emitter instead of forcing a whole-buffer sequential
  scan whenever `--color` is present.
- Output validation checks only records that would be emitted, avoiding a full
  UTF-8 validation pass on ordinary literal searches.
- Recursive list-mode literal matchers scan eligible files as whole buffers,
  eliminating a record split and matcher call per line. Fixed ASCII `-i` in the
  validated C/en/nl UTF-8 locales uses the exact glibc folds into ASCII
  (`U+0131 -> I`, `U+017F -> S`, but not Kelvin) and handles invalid bytes as
  barriers; other locales keep the POSIX fallback. Case-sensitive `-w` searches
  locate whole-buffer byte candidates and ask libc only for their two Unicode
  boundaries. Recursive path strings use one bulk-freed arena. Pipeline paths
  are NUL-terminated in that same arena, so POSIX workers can pass them directly
  to `openatZ` without Zig's per-file `PATH_MAX` stack copy.
- Recursive list scheduling still uses the established files-per-worker rule
  for ordinary trees. Regex matchers without a whole-buffer literal path also
  let trees with fewer than 32 files consider total bytes at a 2 MiB-per-worker
  threshold. This avoids serializing a handful of large binary objects without
  adding thread overhead to literal searches or tiny directories.
- On trees with at least 32 files, workers probe up to 64 KiB with one
  positional read before asking for metadata. A short read proves the complete
  small-file payload and avoids one `fstat`; full probes retain the existing
  `fstat`/mmap path. The stress suite covers empty, short and exact-64-KiB files.
- At 512 regular files, recursive list mode starts a bounded producer/consumer
  pipeline instead of waiting for the complete traversal. Fast literal,
  alternation and required-literal matchers use 12 scan workers; compute-heavy
  regexes without a prefilter retain 16. Workers consume 32-file claims while
  the traversal producer submits 128-file batches; stable arena-owned items
  retain original traversal-order output. Smaller trees keep the previous
  scheduler, and directory recursion opens children relative to their parent
  handle. Interleaved A/B measurements rejected a lower 256-file threshold;
  the later adaptive worker calibration is recorded in the 2026-08-25
  continuation below.
- Recursive full-line output (`-r`, without color, context, `-o`, counts or
  line buffering) now reuses that traversal pipeline in forced-text, default
  binary and without-match modes. Workers discover matches while directories
  are still being walked. Each worker formats into one temporary 64 KiB buffer
  and retains an exact-size copy under a shared 16 MiB payload budget. A file
  exceeding 64 KiB or an aggregate exceeding 16 MiB falls back before
  emission; partial captures are freed before the second bounded window is
  allocated. Matching files containing a NUL also fall back. Invalid UTF-8
  selected records remain suppressed in UTF-8 locales and their binary
  summaries are propagated in traversal order. Trees below 512 files keep
  simple literal/alternation scans sequential; regex-heavy medium trees use
  the bounded ordered worker pool.
- Recursive quiet workers now apply required-literal prefilters to the whole
  file before splitting candidate records. Their density probe is fused into
  that search: absent/sparse files are scanned once, while a dense sample still
  returns to the line matcher before changing semantics. In UTF-8 locales,
  plain ASCII BRE/ERE literals and literal alternations also reuse the byte
  engine only after whole-file ASCII validation; non-ASCII subjects retain
  glibc folding, word-boundary and POSIX semantics.
- `bench/run.sh` accepts `BENCH_LOCALE` and verifies every zgrep/ripgrep result
  against GNU grep before timing it.
- `bench/run.sh` accepts `BENCH_CACHE=cold`; it evicts the persisted input with
  GNU `dd iflag=nocache,count=0` before each timed one-repeat batch.
- `bench/run-tree.sh` also accepts `BENCH_CACHE=cold`. It compiles a temporary
  strict-C walker that requests `POSIX_FADV_DONTNEED` for every regular file in
  one process before each timed batch, avoiding root-only global cache drops
  and per-file process creation. Directory metadata remains warm.
- `bench/run.sh` and `bench/run-tree.sh` accept `BENCH_CPUSET` and execute timed
  commands through `taskset`, which lets this hybrid CPU use only P-cores.
- `bench/run.sh`, `bench/run-null.sh` and `bench/run-tree.sh` accept
  `BENCH_BATCHES`. Values above one report mean, median, p95, minimum and
  maximum across independently timed batches while amortizing timestamp
  process overhead over the requested repetitions.
- `BENCH_PROFILE=ripgrep-sherlock` replays ripgrep's seven English-subtitle
  pattern families on a supplied corpus. `BENCH_PROFILE=ripgrep-linux` replays
  its seven Linux-tree families with POSIX-equivalent classes, `-a` parity and
  exact GNU/ripgrep correctness gates. `BENCH_PROFILE=ripgrep-linux-default`
  replays the same families with each tool's default binary-file mode.

### Exact-byte dense output capture — v0.2

The dense literal restart used commit `7179e03` and its 433,152-byte
ReleaseFast baseline
`272c95ba4bbed93a02524c523b93dfc5b7f1d3cccc5d62f22c78f33a33a390cf`.
On the Linux-header tree, `CONFIG_` selects 5,765 of 16,280 files and produces
3,950,318 output bytes. The old fixed-slot policy exhausted its 16 MiB budget
after 256 matching files because every capture reserved 64 KiB, then rescanned
all 5,765 matches in the ordered output pool.

Two bounded candidates were removed. Reusing only those first 256 fixed
captures was neutral in the 31-by-10 confirmation (23.196 versus 23.316
ms/run). Skipping discovery and running a post-traversal single-pass output
pool lost traversal overlap and regressed dense output to 29.387 ms/run and
sparse output to 26.576 ms/run.

The retained implementation keeps the overlapping discovery pipeline. Each
worker formats one matching file into a temporary 64 KiB stack buffer, reserves
the exact byte count atomically against the shared 16 MiB payload budget, and
copies only those bytes into durable ordered storage. If every output fits,
the main thread emits those buffers directly with no dense rescan. Per-file or
aggregate overflow retains the prior fallback, and partial captures are freed
before the second 16 MiB window is allocated.

The confirming warm `C`, `BENCH_CPUSET=0-15`, 31-batch by 10-repeat lane used
regular-file sinks and GNU correctness gates:

| Dense literal mode | exact-byte capture | `7179e03` baseline | ripgrep |
|---|---:|---:|---:|
| list | 15.719 | 15.671 | 18.012 |
| ordered output | 19.678 | 23.507 | 20.909 |

Ordered dense output improves 16.3% and is 5.9% faster than ripgrep's default
completion-order output on this corpus. A 21-by-5 `C.UTF-8` guard improved from
23.583 to 19.937 ms/run (15.5%), versus 21.205 for ripgrep. Sparse literal
output stayed at 15.527 versus 15.523 ms/run, and the no-literal regex guard at
20.153 versus 20.151. The 147-file `ripgrep/crates` lanes stayed within 1%.

The stress suite now includes 520 matching files whose combined formatted
output exceeds 16 MiB while every individual output stays below 64 KiB. It
proves the aggregate-budget fallback, exact GNU traversal order and byte output
alongside the existing per-file overflow, binary/NUL and invalid-UTF-8 guards.
Debug, ReleaseSafe and ReleaseFast each pass 35 Zig unit tests plus the general,
